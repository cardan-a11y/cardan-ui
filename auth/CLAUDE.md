# Cardan Auth UI layer

This directory is a separate, opt-in Nuxt layer (`@cardan/auth-ui`) with the sign-in and MFA forms for Nuxt SPAs backed by Laravel Fortify. Projects extend it next to Cardan UI, as a peer: `github:cardan-a11y/cardan-ui/auth`. It is not part of the base layer because it adds pages and needs `nuxt-auth-sanctum`, which most projects do not use. Its documentation is [README.md](README.md).

- **Pages**: `/login`, `/forgot-password`, `/reset-password`, `/two-factor-authentication` and `/mfa-setup`, in the `AuthPage` frame (the Cardan Academy design, which Cardan Auditor adopts too). An app overrides a page by creating one at the same path.
- `useCardanAuthConfig` reads the `cardanAuth` app config; the `mfa-setup` middleware and the 403 plugin are behind the setup reminder.
- Copy lives in the layer's `auth`, `mfa` and `password` messages; apps override keys. Buttons use the `black` (main actions) and `ghost` (secondary) variants; there are no button slots.
- The endpoints and the password policy are settings under `cardanAuth` in the app config, with the Cardan Academy API's paths as defaults (`app/app.config.ts`, read through `useCardanAuthConfig()`); an app whose API still serves Fortify's own password routes overrides them in its `app.config.ts`. The forms show their errors in the base layer's ErrorMessage.
- The layer uses the Cardan UI components and tokens only, with no tokens of its own.
- **Sanctum setup** (2.0.0, peer `nuxt-auth-sanctum ^3.1.5`): `nuxt.config.ts` registers the module and sets what every app sets the same (csrf/login/logout endpoints, `client.initialRequest: false`, `keepRequestedRoute`, `onAuthOnly`/`onLogout` `/login`, global middleware on with `allow404WithoutAuth: false`; `prepend` stays off, so the module's middleware runs after every layer's and the app's files), plus the preconnect link from `NUXT_PUBLIC_SANCTUM_BASE_URL` at build time. An app sets `baseUrl`, `origin`, `endpoints.user`, its redirects and any default that differs. With the global middleware on, `sanctum:auth`/`sanctum:guest` do not exist: pages use `sanctum: { guestOnly: true }`. `test/auth/layerConfig.test.ts` builds the fixture apps in `../test/fixtures/auth-app*` to pin the merged config and the middleware order.
- **Identity**: `plugins/identity.client.ts` (`cardan-auth:identity`) asks once, browser only, 10 s timeout, never throws, never replaces a user someone else loaded, and provides `$identityReady`: that promise is the contract, not the plugin's name. A second `provide` of it (an app's own copy) throws at start-up, the one non-additive part of 2.6. `middleware/00.identity.global.ts` awaits it before every other middleware, except on the server and on a route with `meta.waitForIdentity: false`. Global middleware runs per layer (Cardan UI, this layer, the app), by file name within each; an app's file with a layer's name replaces it at the app's place.
- **Language**: `utils/locale.ts`'s `resolveLocale()` (pure, tested as a table) picks the route's `meta.locale`, then `?locale=` on the four signed-out pages for a visitor, then for a signed-in user the first `cardanAuth.localeFields` entry the app offers; `null` leaves the language. `01.locale.global` applies it on navigation (the profile only on the first one and when leaving a route with its own language), `plugins/profile-locale.client.ts` when the user object changes to another profile language; both share `useState('cardan-auth:profile-locale')`, cleared on sign-out, so a switch by hand stays for the session. `plugins/accept-language.ts` sends the locale on every Sanctum request. No visitor memory, no storage.
- `isAuthPage(path)` and `AUTH_PAGES` (`utils/authPages.ts`, `/mfa-setup` included) plus `cardanAuth.authPages` (exact, or a prefix ending in `/`); the signed-out list for `?locale=` is separate and internal. `cardanAuth.themeField` (off by default) sets `useColorMode().preference` on every new user object (`plugins/profile-theme.client.ts`); color mode comes from Cardan UI, not this layer. `useLogoutDialog().open()` waits one task, so a closing menu hands focus back first.
- The demo is the Auth UI section of the playground (`/auth`), backed by mock Fortify endpoints in `../.playground/server/routes` (sign-in and sign-out under `/api/`; the identity endpoint answers 401 until the sign-in challenge sets the `demo-session` cookie, so a visitor is a guest); its pages render client-side only, like the SPAs that use the layer. The playground turns the global middleware off and sets `waitForIdentity: false` on its documentation pages in `pages:extend`.
