# Cardan UI

Accessible Vue 3 component library for Nuxt 4 in TypeScript, distributed as a [Nuxt Layer](https://nuxt.com/docs/getting-started/layers). cardan-lms-nuxt (Cardan Academy), cardan-auditor-nuxt, cardan-cms-nuxt and cardan-support-nuxt extend it: `github:cardan-a11y/cardan-ui` (`main`, untagged) in production and `../cardan-ui` in development. A merge here reaches all of them at their next build.

The shared Cardan guidelines (the review before every commit, CSS, code quality, WCAG 2.2) come from the `cardan` Claude Code plugin, which adds them to every session in a Cardan repository. This repository is the plugin's home: [plugins/cardan](plugins/cardan/) holds the guidelines skill, the `cardan:cardan-reviewer` agent (and `cardan:plugin-reviewer` for a change to the plugin alone), the review hook, the `release`, `pr-body` and `i18n-pair` skills, a Playwright MCP server and the cross-browser check of the review round (`scripts/cross-browser.mjs`), and [.claude-plugin/marketplace.json](.claude-plugin/marketplace.json) lists it as the `cardan-ui` marketplace, next to [plugins/cardan-browsers](plugins/cardan-browsers/): Firefox and WebKit MCP servers, off by default, switched on with `/plugin` to look into a difference the cross-browser check found. The projects enable it in their `.claude/settings.json` and take a new version with `claude plugin update cardan@cardan-ui --scope user`. To try a change to the plugin here, run `/reload-plugins` in a session that reads it from this checkout (`claude plugin list` shows where it reads from), or start one with `claude --plugin-dir ./plugins/cardan`. `claude plugin validate ./plugins/cardan` checks it.

## Working here

- **Branches**: `main` is what the projects build from. Work starts on the release branch of the next patch version, `release/<version>`, cut from `main`: fixes are bundled there until `/cardan:release` makes them a version and opens the pull request, and after the merge the next release branch is cut. A change that must reach the projects before the rest gets its own branch and pull request. Releases are not tagged.
- **Checks**: `pnpm run lint`, `pnpm run typecheck` (vue-tsc over the playground's generated project; it passes on `main`, so a type error is a signal) and `pnpm test` (vitest in the playground's Nuxt environment, with axe through `test/a11y.ts`). CI runs all three on every pull request and on `main`. There is no review in GitHub Actions: the local review before every commit is the review.
- **Done means**: the checks pass; the change was tried in the playground with the keyboard, at 320px and at desktop width, in both locales and both color modes (the plugin's Playwright MCP server does this in Chrome from the session; the review round runs its cross-browser check in Chrome, Firefox and WebKit); a changed component with a test has its test updated; the local review ran and its tally is in the PR description (`cardan:pr-body`).
- **Release**: `/cardan:release`: the version in `package.json`, an entry in [.playground/pages/changelog.vue](.playground/pages/changelog.vue), a section in [MIGRATION.md](MIGRATION.md) with what projects must do (one line when they need to do nothing), then the PR. In cardan-lms-nuxt and cardan-auditor-nuxt the same skill takes work that has not reached `develop` yet (uncommitted changes, or a branch with an open PR into `develop`) through its own reviewed PR first, with the version and release notes PRs, then opens the release PR from `develop` into `main`.
- **The review gate** only sees the commands Claude runs: a push from your own terminal is not gated.
- **Machine-specific**: the projects are checked out next to this one in `~/Development` and extend `../cardan-ui`; the playground runs on port 3003 (`pnpm dev`). A cloud session has only this repository and the playground.

## Components

One file per component in [app/components/](app/components/), auto-imported by file name. The playground at `http://localhost:3003` ([.playground/pages/](.playground/pages/)) shows nearly all of them with live examples of most props. What a listing cannot show:

- **MarkdownPreview** ([app/components/Markdown/](app/components/Markdown/), markdown-it; highlight.js with the grammars in `highlight.ts` loads after mount, only when a text has a code block) is safe by default: raw HTML shows as text and `{…}` sets only `lang`, `dir` and `class`; `trusted` allows both, for text the team wrote. `inline` renders a title or label in a `<span>`, `heading-offset` moves headings down. A bare YouTube or Vimeo link in a paragraph of its own renders as VideoPlayer, also without `trusted`; a link with its own text, or one in an `inline` text or with `videos-as-links` (a table cell), stays a link. A link opens in a new window only when it goes to another origin. **MarkdownEditor** wraps md-editor-v3.
- **VideoPlayer** plays YouTube and Vimeo videos: a thumbnail and a play button first, the player after a click. `parseVideoUrl()` in [app/utils/video.ts](app/utils/video.ts) decides which URLs it plays, for MarkdownPreview too. It needs `@nuxt/image` in the project, which the layer does not register, with the thumbnail hosts in its `image.domains`: `['i.ytimg.com', 'i.vimeocdn.com']`.
- **CardanLogo**: full, symbol and tile forms, color variants and product lockups (`product="academy"` shows "| Academy"; the product name is always Hanken Grotesk, in Body or white, never purple). 20px high by default; in a flex row a lockup takes the room it gets, from 144px (`narrow-width`) up to its height. The favicon is the light round tile with the symbol at 72%.
- **Accordion** is the APG accordion: a button in a heading (`h-tag`) that opens a panel, inert while closed and a `region` landmark only with the `region` prop; the panel's overflow follows its state, so nothing in it is clipped once open. **AccordionDetails** is the native `<details>`.
- **FormField** is the frame the field components share: the label with its required chip, the control in its slot, the error text and the instruction, with the styles they share. A new field component renders through it and points its control at `instruction-<id>` with `aria-describedby`, and at `error-<id>` only while the error shows: after a failed submit of its Form (`formShowInvalidKey`, which Form provides) or with `show-invalid`. `error-message` is the text for a constraint the browser checks; `custom-error` shows an error the browser cannot find, such as one from the server, and describes the field by it until its value changes, without holding the form back. An attribute on Input, Textarea or Select goes to the control, `class` and `style` to the wrapper.
- **Dialog** is a native `<dialog>`, opened and closed through its exposed `openDialog()` and `closeDialog()`, and `--dialog-max-width` on its class sets its width (800px at the side by default; a centered dialog without it is as wide as its content); **Tooltip** and **Popover** use the native Popover API and CSS anchor positioning (README has the browser baseline); Popover is a disclosure (a list of links or buttons, no menu roles): when it opens focus moves to its first item, Tab past the last leaves and closes it, Escape returns focus to the trigger; **Callout** has `solid` (default) and `outline` variants; **FocusLoop** keeps Tab in a container and, when modal, makes the rest of the page `inert` while it is open (the component that can break a whole page: its tests in `test/components/FocusLoop.test.ts` cover every way it opens and closes); **MultiSelect** wraps @vueform/multiselect, **DatePicker** wraps Vue DatePicker, **FileInput** compresses images with compressorjs; with `mode="document"` it checks a file against the extensions in `accept` and hands it to the parent to upload (`select`), uncompressed, and `shape="circle"` is the avatar upload.
- **ErrorMessage** is the error box of a form or a page, in every project and the auth layer. `extractApiError()` ([app/utils/api.ts](app/utils/api.ts)) reads what a failed request threw, in either shape the Laravel APIs answer in (Laravel's `{ message, errors: { field: [...] } }`, the JSON:API envelope of the Academy's `/api/v1`), with the `Content-Language` (English without one); `useErrorMessage()` keeps it as `errorData` for the box. Without a usable answer the box says, in the page's language, that the browser was offline (read from `navigator.onLine` as the request fails, so the text does not change when the connection comes back) or that something went wrong (an HTML error page, a server that did not answer). Its `text` prop is page text, shown before the API's messages; it takes no outer margin.
- **Composables** in [app/composables/](app/composables/): `useToast()` queues the toasts that **ToastManager** shows and hides one by its id; `useCookiesDialog()` holds the cookie consent that **CookiesDialog** collects and applies (it loads GTM, with `runtimeConfig.public.gtmId`), and the open flag the dialog follows (`openCookiesDialog()`), so any component reads it without repeating that work; `useScreenSize()` exposes the breakpoints and the pointer type as refs; `useDate()` formats relative dates in the current locale.
- **Utilities** in [app/utils/](app/utils/): `api`, `datetime`, `file`, `markdown`, `sort`, `video` and `index`. Shared types are `declare global` in [app/types/index.ts](app/types/index.ts).

## Cardan Auth UI layer

The [auth/](auth/) directory is a separate, opt-in Nuxt layer (`@cardan/auth-ui`) with the sign-in and MFA forms for Nuxt SPAs backed by Laravel Fortify. Projects extend it next to Cardan UI, as a peer: `github:cardan-a11y/cardan-ui/auth`. It is not part of the base layer because it adds pages and needs `nuxt-auth-sanctum`, which most projects do not use. Its documentation is [auth/README.md](auth/README.md).

- **Pages**: `/login`, `/forgot-password`, `/reset-password`, `/two-factor-authentication` and `/mfa-setup`, in the `AuthPage` frame (the Cardan Academy design, which Cardan Auditor adopts too). An app overrides a page by creating one at the same path.
- **Components**: `AuthPage`, `LoginForm`, the password forms, `MfaSettings`, `LogoutDialog`, `PasswordConfirmationDialog` and the MFA flow (`MfaChallenge`, `MfaSetup`, `MfaDialog`, `MfaQr`, `MfaCode`, recovery codes, …).
- **Composables**: `useAuth`, `useMfa`, `useMfaDialog`, `usePasswordConfirmation`, `useMfaSetupReminder`, `usePasswordPolicy`, `useLoginEmail`, `useLogoutDialog`, `useCardanAuthConfig` (wrapping `nuxt-auth-sanctum` and the app config), plus the `mfa-setup` middleware and the 403 plugin behind the setup reminder.
- Copy lives in the layer's `auth`, `mfa` and `password` messages; apps override keys. Buttons use the `black` (main actions) and `ghost` (secondary) variants; there are no button slots.
- The endpoints and the password policy are settings under `cardanAuth` in the app config, with the Cardan Academy API's paths as defaults (`auth/app/app.config.ts`, read through `useCardanAuthConfig()`); an app whose API still serves Fortify's own password routes overrides them in its `app.config.ts`. The forms show their errors in the base layer's ErrorMessage.
- The layer uses the Cardan UI components and tokens only, with no tokens of its own.
- The demo is the Auth UI section of the playground (`/auth`), backed by mock Fortify endpoints in `.playground/server/routes`; its pages render client-side only, like the SPAs that use the layer.

## CSS variables

All global CSS variables for color, spacing, typography, etc. are declared in [main.css](app/assets/main.css). The layer does not load this file: it is the Cardan template that each consuming project copies into its own `main.css` (a stylesheet shipped by the layer would add a render-blocking request). The playground imports it from [playground.css](.playground/assets/playground.css).

- The `--cardan-*` primitives hold the brand palette; components never use them, only the semantic `--color-*` tokens do.
- Custom properties that a component sets for itself, such as from a `fontSize` or `iconSize` prop, are prefixed with the component name (`--button-icon-size`, not `--icon-size`), so they don't leak into nested components.
- A component reads a shared token bare, `var(--color-text)`, so a missing token shows up instead of being papered over: no `var(--new-token, var(--old-token))` chains. When a component needs a new token, add it to `main.css` and to the release's section in [MIGRATION.md](MIGRATION.md), with a value that keeps the current look of existing projects. A fallback is fine where it is the default of a component's own property that a prop or a parent may set, `var(--button-radius, var(--radius-md))`.
- Every text and graphic token pair must meet WCAG 2.2 AA contrast (4.5:1 for text, 3:1 for graphics) in light and dark mode. Never fix a contrast failure by inventing a new color; use a brand token.
- Text and icons on tinted (`-bg`) surfaces use the matching `--color-*-text` token; every `-text` token must reach 4.5:1 on its `-bg` surface.

## Icons

Components take an `icon` prop, powered by [@nuxt/icon](https://nuxt.com/modules/icon) and Iconify. Use [Material Symbols](https://icones.js.org/collection/material-symbols): `material-symbols:<name>-outline-rounded` first, `-rounded` when the design wants a filled icon, the plain name when neither variant exists. Icons are decorative (hidden from screen readers) unless the component has no text label, so give an icon-only control an `aria-label`. An icon a component shows on first paint goes into `bundledIcons` in [app/utils/icons.ts](app/utils/icons.ts), which the layer's `nuxt.config.ts` puts in the client bundle of every project, so the page does not shift when it loads. A listed icon whose collection a project does not install fails that project's production build, so it comes from Material Symbols or `svg-spinners`, which every project installs.
